## 第一部分：系统流程介绍

### 1.1 文档摄入流程（数据入库）

```
用户上传 → FastAPI 接收 → MinIO 存储 → Celery 异步入队
                                          ↓
                            ingest-worker（独立容器）
                              ├─ PipelineFactory 按文件类型路由
                              ├─ PDF: pdfplumber 提取文本+表格
                              ├─ 扫描页 Tesseract OCR 回退
                              ├─ 嵌入图片 pytesseract OCR（独立脚本）
                              ├─ 文本清洗（中文去重/页码/连字符/控制符）
                              ├─ 智能分块（段落边界优先，target=600, overlap=100）
                              ├─ AC 自动机关键词标注（L0-L4 + tags）
                              └─ 写入 PostgreSQL + 入队 embed-worker
                                          ↓
                            embed-worker（独立容器）
                              ├─ 调 embedding API（yunwu.ai）
                              └─ 写入 Milvus / pgvector
```

**覆盖文件类型：** PDF、DOCX、PPTX、XLSX、图片、音频、TXT/MD/HTML、JSON。

### 1.2 检索问答流程

```
用户输入 query → 前端 POST /api/v1/chat/stream
                     ↓
        三层缓存命中检查（默认关闭: SHA256 → pgvector 语义 → Jaccard）
                     ↓
        双路并行检索
          ├─ Milvus ANN（HNSW 索引 + 权限过滤表达式）
          └─ PostgreSQL BM25（tsvector + zhparser GIN 索引）
                     ↓
        RRF 融合（k=60）→ 文档级去重（per_doc_limit=2）
                     ↓
        L1-L5 权限过滤（DB 层前置过滤 + 应用层逐行校验）
                     ↓
        Cross-Encoder Rerank（yunwu.ai qwen3-rerank）
                     ↓
        SecurityGateway 三级策略（L4→本地 / L3→脱敏 / L2→直调）
                     ↓
        LLM 生成（DeepSeek-v4-flash / MiniMax-M3）
          └─ 流式输出 + AC 自动机实时关键词拦截
                     ↓
        SSE 流式返回前端 → 候选面板展示 → 工程师可参与排序
```

### 1.3 Prompt 结构与上下文工程

当前输入 LLM 的 Prompt 结构：

```
System Prompt（稳定段，不随对话变化）:
  "你是一个企业级私有RAG助手。请基于以下检索到的上下文回答用户问题。
  注意事项：
  1. 仅使用提供的上下文，不要编造信息
  2. 如果上下文不足，请明确说明
  3. 注意上下文中的权限标记，不要泄露超出用户权限级别的敏感信息
  4. 引用来源时标注[doc_index]"

多轮对话历史（动态段，按时间顺序排列，超预算时压缩）:
  {"role": "user", "content": "..."}
  {"role": "assistant", "content": "..."}

当前用户请求: 
  {"role": "user", "content": "上下文：
    [0] <perm level="L2"/> UPS5000-E 功率模块额定容量20kVA...
    [1] <perm level="L1"/> 安装环境要求：设备应安装在远离液体的区域...
    
    问题：UPS5000E工作模式_维修旁路是什么"}
```

上下文工程的设计目标是让 Prompt 具备**结构化、可裁减、带权限标记**的能力。基于 `docs/design/工程师反馈与上下文工程设计.md` 的分层设计：

| 层级 | 内容 | 特性 |
|------|------|------|
| **稳定段** | System Prompt、系统规则、工具说明 | 不随对话变化，可缓存复用 |
| **检索上下文** | 当前检索到的 chunks | 带 `<perm level="Lx"/>` 权限标记，LLM 据此控制信息泄露 |
| **对话历史** | 多轮 user/assistant 交互 | 按时间轮次排列，超预算时从最早的轮次开始压缩为摘要 |
| **当前请求** | 最新的用户 query | 永不裁减 |

**上下文裁剪策略**（`_trim_history`）：当总字符数超出预算（`max_context_tokens × 3`）时，预算分配优先级为 `query > system > context > 近期完整历史 > 早期摘要`。从最早的对话轮次开始，将一对 (user, assistant) 压缩为单行 `[历史] Q: ... A: ...` 摘要。

### 1.4 工程师反馈闭环

基于 `docs/design/工程师反馈与上下文工程设计.md` 的五层架构：

```
第一层：Rerank 候选展示与交互
  └─ 前端展示 Top-3 候选，工程师可调整排序、编辑答案、提交反馈

第三层：缓存命中与相似查询匹配（待接入）

  └─ 后续相似 query 跳过检索+LLM，直接命中缓存

第四层：上下文分层管理（初版已实现）
  └─ 稳定段/动态段分离，权限标记内联
  └─ 超预算时按优先级裁减

第五层：上下文瘦身与预算控制（初版已实现）
  └─ _trim_history 从最早轮次开始压缩
  └─ 预算分配: query > system > context > 近期历史 > 早期摘要
```

#### 查询改写（07-21）

问题：eval 和 web 行为不一致——eval 的 keyword 带改写但 web 不带，导致 web keyword MRR 比 eval 低 24%。

修复：将 `rewrite_query()` 提升为 backend 单一来源，剥离疑问词/停用词（"是什么问题"、"怎么"、"有哪些"），只对 keyword 模式生效，semantic/hybrid 不改写。改写后 query 同时用于 BM25 与 Rerank。

效果：keyword MRR +24%，web 与 eval 行为对齐。

#### 中文分词修复（07-02 → 07-03）

- 索引和查询统一使用 `chinese`（zhparser）分词，重建全量索引
- 清理重复文档（每个文件只保留最新一个）
- recall@1 从 0.000 恢复至 0.720

### 2.3 Phase 2 核心：上下文工程与工程师反馈

#### 工程师反馈闭环

基于 `工程师反馈与上下文工程设计.md` 的五层架构，已实现第一、二、四、五层：

**已实现的交互流程：**

```
检索 → Rerank → 候选列表 → 前端展示 Top-3
                              ↓
                 工程师可: 调整排序 / 编辑答案 / 提交反馈
                              ↓
                 反馈持久化 → engineer_feedback 表
                              ↓
                 同时更新 messages.candidates 字段
```

#### 候选展示（`candidates` 字段）

每条 assistant 消息附带 `candidates` 数组，包含 rank、rerank_score、chunk_id、content。前端按 rank 展示三个候选结果，工程师可逐条操作。

#### 反馈数据结构

```python
engineer_feedback:
  query: str               # 原始 query
  chosen_rank: int         # 工程师选中的 best rank
  ranking: JSONB           # 完整排序列表 [chunk_id, ...]
  ratings: JSONB           # 逐候选评分 {chunk_id: score}
  action: str              # rank / approve / edit / force_refresh
  edited_answer: str       # 工程师修改后的答案
  comment: str             # 备注
```

#### 上下文裁剪（`_trim_history`）

多轮对话超预算时，从最早的对话轮次开始压缩为单行摘要，保证最新的 query 和检索上下文完整。优先级：`query > system > context > 近期完整历史 > 早期摘要`。

### 2.4 Phase 2 核心：系统安全与工程化

#### 五级权限体系（L1-L5）

| 层级 | 控制粒度 | 过滤时机 | 过滤位置 |
|------|---------|---------|---------|
| L1 文件类型 | 用户可访问的文件类型 | 检索前 | 数据库层（Milvus expr / PG WHERE） |
| L2 文档级别 | 用户对单篇文档的访问 | 检索前 + 检索后兜底 | 数据库层 + 应用层 |
| L3 字段/列级 | Excel 列 / Word 段落 | 检索后 | 应用层逐行校验 |
| L4 标签级别 | 基于标签的黑白名单 | 检索前 | 数据库层 |
| L5 关键词敏感 | chunk 内容中的关键词级别 | 检索后 | 应用层 level 比较 |

L5 关键词敏感级别通过 AC 自动机在文档摄入时自动标注 chunk 敏感级别（L0-L4），检索时比较 `user_level` 和 `chunk_level`，越级内容替换为 `"[内容涉及更高敏感级别，已过滤]"`。这是当前唯一实际生效的权限层级。

#### SecurityGateway 三级 API 策略

- **L4 及以上**：本地处理，禁止调用外部 LLM API
- **L3**：实体脱敏后调用 API（手机号/身份证/邮箱替换为占位符）
- **L2 及以下**：直接调用外部 API

#### AC 自动机流式关键词拦截

流式生成场景，每输出一个 token 检查最近 200 字符，命中敏感关键词则截断输出。关键词库通过管理员页面动态管理。

#### Prometheus 全链路埋点

| 指标 | 标签 | 用途 |
|------|------|------|
| `rag_api_request_duration_seconds` | method, endpoint | API 延迟分布监控 |
| `rag_retrieval_duration_seconds` | mode | 检索耗时（hybrid/semantic/keyword） |
| `rag_generation_duration_seconds` | model, status | LLM 生成耗时 |
| `rag_rerank_total` / `rag_rerank_reordered_total` | mode | Rerank 排序变化统计 |
| `rag_zero_result_total` | mode | 0 结果告警 |
| `rag_top_doc_concentration` | mode | 文档集中度监测 |
| `rag_rerank_fallback_total` | mode | Rerank 回退告警 |

#### 三层查询缓存

三层缓存（SHA256 → pgvector 语义 → 关键词 Jaccard）代码已完成，支持安全级别隔离（低权限用户不命中高权限缓存）。当前默认关闭（`ENABLE_QUERY_CACHE=False`），待上线评估后开启。

#### 2.5.3 Bad Case 分析

**类型 A：语义检索盲区——Q7（MDU显示屏接口）**

```
问题: semantic 模式下 Top-10 完全不包含期望 chunk83/84
      hybrid 也只命中 chunk84（rank#2），chunk83 不在 Top-10
根因: "MDU" 在文档中为全称 "监控模块"，语义向量匹配时
      "MDU" 缩写与 "监控模块" 的向量距离不够近
优化方向: 查询改写时对缩写做扩展（MDU → 监控模块），或元数据增强
```

**类型 B：关键词检索黑障区——Q2（RF_Z）、Q8（母线电压）**

```
Q2 关键词模式: 返回 0 结果
根因: query 包含特殊字符 "RF_Z"，BM25 tsvector 无法分词，
      jieba 降级也无法处理 "RF_Z"
优化方向: 查询改写时对特殊字符做归一化，或增加 query 预处理规则

Q8 关键词模式: 返回 0 结果
根因: "母线电压未升起" 为长尾工程术语，zhparser 分词
      无法有效匹配文档中的表述
优化方向: 结合语义检索（hybrid 模式下 Q8 3 个期望全命中）
```

**类型 C：语义检索漂移——Q4（输出开关断开）**

```
问题: semantic 模式 Top-10 全部是 "输出开关" 相关但非告警类 chunk
      期望 chunk654/655（告警编号相关）被 rerank 排到后面
      keyword 和 hybrid 正确命中（chunk655#1）
根因: "输出开关断开" 语义上容易匹配到大量 "输出开关" 相关内容，
      而精确的告警编号匹配依赖关键词
结论: 该 query 依赖 hybrid 双路互补，纯 semantic 不够
```

**类型 D：多文档长尾——Q10（电池冷启动）**

```
问题: 初版标注 chunk73 实际不相关，在 q10fix 版本中移除
      semantic 模式 chunk164 在 rank#7，不在 Top-5
优化方向: 标注质量对评测结果影响大，需人工验证每个 expected chunk 的准确性
```

#### 2.5.4 三模式对比分析

```
hybrid（双路融合）  vs  semantic（纯向量）  vs  keyword（纯 BM25）
  MRR: 0.883          MRR: 0.604           MRR: 0.600
  P@1: 0.800          P@1: 0.500           P@1: 0.500

6 条 query 三种模式表现一致: Q1/Q5/Q6/Q9 均稳定命中
2 条 query hybrid 优势明显:  Q4（keyword 补 semantic 盲区）
                              Q2（semantic 补 keyword 盲区）
2 条 query 所有模式均偏弱:   Q7（缩写问题）/ Q8（长尾术语）
```

**结论：hybrid 模式有效融合了两路优势，是当前检索链路的最佳选择。** 纯 semantic 或纯 keyword 各有盲区，双路互补性验证成立。后续优化重点是 Q7 类型的缩写-全称匹配和 Q8 类型的长尾工程术语理解。

## 第三部分：后续方向

### 3.1 测试集扩展与标注规范

当前 10-20 条 query 的评测集统计意义有限。扩展到 100+ 条时需建立标注规范：

- **标注到 chunk 级别**：仅标注文件名的 query 会导致 recall/NDCG 虚低
- **多标注验证**：每条 query 的 expected chunk 经人工验证
- **持续集成**：检索逻辑变更自动跑评测，MRR 低于基线阻止合并

### 3.2 工程师反馈接入缓存

当前反馈数据只存储，未写回 query_cache。下一阶段将已确认的反馈（action=approve）作为 best_answer 写入缓存，高频 query 跳过检索和 LLM。需要解决：

- 文档更新时的缓存主动失效策略（当前无版本号机制）
- 缓存置换策略（LRU + TTL 自然过期）

### 3.3 上下文裁剪完善

初版 `_trim_history` 已实现最早轮次压缩，但完整方案 `docs/design/` 中的权限感知压缩策略尚未完全接入。待完善：

- `CompressionService.compress_chunks()` 的 `permission_aware` 策略接入生成流程
- 同权限级别 chunk 分组压缩，不同级别用 `<chunk level="Lx">` 包裹
- 低相关度 chunk 做头尾截断，高相关度保留完整

### 3.4 数据清洗与元数据增强

当前清洗规则覆盖 PDF 技术文档的确定性噪声。生产化需：

- 建立"LLM 辅助发现 → 正则规则 → 全量跑 → 抽样验证"的迭代循环
- 补充 Confluence 元数据、论坛标记、Word 修订记录等噪音类型
- 对每份文档用 LLM 生成摘要 + 技术术语 + 可回答问题列表，配合 HyDE 检索策略

### 3.5 图片展示进阶

当前仅提取图片文字，下一阶段让用户直接看到图片：PDF 解析时提取嵌入式图片 → 上传 MinIO → 记录 URL → LLM 回答中引用 → 前端渲染。存储方案可通过 MinIO + HTTP URL 实现，浏览器可缓存，后续接 CDN。

### 3.6 模型与延迟优化

当前最佳配置（07-28 实测）：

| 模型 | 总耗时 | 首 token | 检索 | LLM 生成 |
|------|--------|---------|------|---------|
| DeepSeek-v4-flash | **13.9s** | ~7s | 7.4s | 6.5s |
| MiniMax-M3 | **34.1s** | ~6s | 6.0s | 28.1s |

瓶颈在 API 代理层（yunwu.ai embedding 2-3s + rerank 3-4s），本地计算 <0.5s。后续：Rerank 快速降级、打开查询缓存、寻找更稳定的 embedding/rerank 服务。

## 四、开发环境与部署

### 4.1 当前部署（轻量模式）

当前运行的是 `docker-compose.lightweight.yml`，共 5 个容器：

```
rag-lw-postgres     # PostgreSQL 16 + pgvector + zhparser（向量+全文检索）
rag-lw-app-backend  # FastAPI 后端
rag-lw-frontend     # React 前端
rag-lw-worker       # Celery Worker（文档解析+向量化+评测）
rag-lw-redis        # Redis（缓存+Celery Broker）
```

**与完整模式的差异：**

| 组件 | 轻量模式（当前） | 完整模式 |
|------|----------------|---------|
| 向量库 | PostgreSQL pgvector（内嵌） | 独立 Milvus 2.4 集群 |
| 消息队列 | Redis（Celery broker 复用） | RabbitMQ 独立 |
| 文件存储 | 本地文件系统 | MinIO 对象存储 |
| API 网关 | 无（前端直连 backend） | Kong |
| 监控 | Prometheus 指标在进程内存 | Prometheus + Grafana + AlertManager |

向量检索在轻量模式下通过 pgvector 的 HNSW 索引完成，Milvus 非必需。两种模式切换只需改 `VECTOR_STORE_BACKEND=milvus|pgvector`。

```bash
# 启动/停止

docker compose -f docker-compose.lightweight.yml down

# 查看日志
docker logs -f rag-lw-app-backend

# 重启后端（代码修改后需要）
docker restart rag-lw-app-backend

### 4.4 接手建议优先级

| 优先级 | 事项 | 原因 |
|--------|------|------|
| P0 | embedding/rerank API 稳定性 | 当前 yunwu.ai 偶发超时，影响首 token（正常 7s，异常 50s+） |

| P2 | 评测集扩展到 100+ query | 当前 20 条统计意义有限，且标注未完全对齐到 chunk 级 |
| P2 | OCR Worker 自动化 | 当前为手动脚本，线上需 Celery 独立队列 |
| P3 | 上下文裁剪完整方案 | CompressionService 权限感知策略已设计，待对接生成流程 |
