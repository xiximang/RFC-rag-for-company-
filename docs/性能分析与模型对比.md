# 性能分析与模型对比

> 基于 2026-07-24 实际测试数据
> 知识库: ups-eval-kb（20 文档，全 indexed）
> Query: 取自 eval_retrieval_ups.py 的 Q1-Q5

---

## 定义

- **端到端首 token 时间**：用户点击发送 → 看到第一个字符（流式）
- **端到端总耗时**：用户点击发送 → 全部回答加载完毕
- **各阶段说明**：

```
  embedding API（查询向量化）
       ↓
  Milvus ANN 检索（向量相似度搜索）
       ↓
  BM25 全文检索（关键词匹配）
       ↓
  RRF 融合（两路结果合并）
       ↓
  Chunk 加载 + 权限过滤（L1-L5）
       ↓
  Rerank（Cross-Encoder 精排）
       ↓
  SecurityGateway 策略决策
       ↓
  LLM 生成（首 token → 逐字输出）
```

## 链路耗时拆解（基于实测）

### 检索阶段（不含 LLM 生成）

纯检索接口测试结果：

| 模式 | 耗时 | 说明 |
|------|------|------|
| 纯语义检索（含 Rerank） | **8.3s** | embedding + Milvus + Rerank |
| 纯语义检索（不含 Rerank） | **4.8s** | embedding + Milvus，走 yunwu.ai 中转站 |

### 各环节估算耗时

实测值（三次取平均）：

| 环节 | 平均耗时 | 说明 |
|------|---------|------|
| embedding API（yunwu.ai） | **2.5s** | 正常范围 2-3s，偶发冷启动可达 138s |
| Milvus ANN + BM25 + RRF + 权限过滤 | **~2-3s** | 纯检索阶段，含 docker 网络开销 |
| Rerank API（yunwu.ai qwen3-rerank） | **~3.5s** | 单次 batch 送 15 个候选 |
| LLM 生成: MiniMax-M3 | **6-13s** | 方差大，受回答长度和 API 影响 |
| LLM 生成: DeepSeek-v4-flash | **3-8s** | 方差更小，比 MiniMax 稳定 |

```
端到端 10-20s 的分布（正常 embedding 场景）:
  ┌─ embedding API（yunwu.ai）:      ~20%  (2-3s)
  ├─ 检索（Milvus+BM25+过滤）:       ~20%  (2-3s)  
  ├─ Rerank API（yunwu.ai）:         ~25%  (3-4s)
  └─ LLM 生成:                       ~35%  (3-13s，取决于模型和回答长度)
```

## 模型对比：DeepSeek-v4-flash vs MiniMax-M3

### 正常 query 对比（Q3/Q4/Q5）

| Query | MiniMax | DeepSeek | 差距 |
|-------|---------|----------|------|
| Q3 电池电压低关机 | 16.0s | 10.8s | DeepSeek 快 **32%** |
| Q4 输出开关断开 | 25.3s | 13.5s | DeepSeek 快 **47%** |
| Q5 维修旁路 | 13.6s | 13.0s | 持平 |
| **平均** | **18.3s** | **12.4s** | **DeepSeek 快 32%** |

### 主要差异

| 维度 | MiniMax-M3 | DeepSeek-v4-flash |
|------|-----------|-------------------|
| 生成速度 | 方差大（13-56s） | 方差小（10-15s） |
| 长尾 query | Q1 55s、Q4 25s | Q1 14.5s、Q4 13.5s |
| 稳定性 | 偶发卡慢 | 各 query 耗时相对均匀 |
| API 通道 | 直连 minimaxi.com | 通过 yunwu.ai 中转站 |

### 结论

> MiniMax-M3 和 DeepSeek-v4-flash 在正常 query 上的平均总耗时差约 30%，**但更显著的差异是方差**——MiniMax 有偶发卡慢（55s），DeepSeek 各 query 之间更稳定。

## 当前瓶颈分析

### 瓶颈排序

```
首 token 时间瓶颈占比（正常 embedding 场景）:
1. Rerank API (yunwu.ai):       ~3.5s  → 单次调用，不可跳过
2. 检索计算（Milvus+BM25+过滤）: ~2-3s  → Docker 环境网络开销
3. embedding API (yunwu.ai):     ~2.5s  → 正常范围，偶发异常
4. LLM 首 token:                 ~1-3s  → 取决于模型
```

### 说明

- **Rerank 是首 token 等待的最大单项**，每次检索必经，约 3.5s
- 检索计算 2-3s 在 Docker 环境下属于可接受范围，但相比纯裸机预期（~300ms）有 Docker 网络和 PG 连接开销
- embedding API 正常响应在 2-3s，不属于异常范围。138s 偶发情况需要关注但非普遍问题
- LLM 生成影响的是**首 token 之后的总耗时**，不是首 token 等待时间

## 后续优化方向

| 方向 | 预期效果 | 优先级 |
|------|---------|--------|
| 换稳定的 embedding API | 首 token 从 >10s 降到 1-3s | P0 |
| 换稳定的 rerank API | 每轮请求省 3-4s | P1 |
| 打开查询缓存 | 高频 query 直接命中，跳过全部检索 | P1 |
| 换更快 LLM（DeepSeek） | 生成阶段省 30%，方差更小 | P2 |
| Rerank 降级策略优化 | 失败时快速 fallback，不等待重试 | P2 |
