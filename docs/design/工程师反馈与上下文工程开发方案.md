## 2. 五级穿透兼容总原则（贯穿所有步骤）

每一步新增功能都必须遵守，违反任一条即视为破坏五级穿透：

| 编号 | 原则 | 落地方式 |
|------|------|---------|
| P1 | **候选/缓存/反馈内容一律复用检索阶段已穿透的结果** | 直接用 `retrieval_service.search` 返回的 item，不重新查 Chunk 表 |
| P2 | **content 取降级后的值** | 显式用 `item["content"]`（L5 已替换为占位符），**绝不按 chunk_id 反查原文** |
| P3 | **不引入新的权限判断** | 不自己调 `permission_service` / `intercept_response`，避免与五级形成双份逻辑 |
| P4 | **缓存条目继承检索时的权限上下文** | 缓存 key/匹配必须带用户安全等级维度，低权限用户不能命中高权限用户的缓存 |
| P5 | **反馈回流不绕过降级** | 工程师编辑的答案、确认的最佳答案写入存储前，按当前 reviewer 的安全等级再过一次 L5 校验 |
| P6 | **只加不改不删** | 新功能尽量新增文件/字段/端点；对现有函数只做"附加返回字段"或"新增可选分支"，不改动其主流程；**禁止删除任何文件/脚本** |

## 4. Phase 2 — 查询缓存 + 相似匹配

**Phase 2 目标：** 高频/相似查询命中缓存跳过 rerank+LLM；缓存带 freshness 自动失效；缓存按安全等级隔离，低权限不能命中高权限缓存。

### Step 2.1 query_cache 表 + ORM + 迁移

**改动文件：**
- `backend/app/models/query_cache.py` — **新建**。字段按设计稿 §9.1，**增加 `owner_security_level VARCHAR(8) NOT NULL`**（缓存条目所属安全等级，P4 隔离用）。`query_embedding vector(1536)`。
- `backend/alembic/versions/2026_07_21_add_query_cache.py` — **新建**迁移：建表 + `ivfflat` 索引 + `query_hash` 唯一索引 + `query_keywords` GIN 索引 + `owner_security_level` 普通索引。检查 pgvector extension。
- `backend/app/services/cache_service.py` — **新建** `CacheService`：`get_by_hash` / `search_by_embedding` / `list_recent` / `upsert` / `evict`。纯数据访问层，不含匹配策略。

**五级兼容：** P4。表结构带 `owner_security_level`，为隔离打基础。

**测试（后端）：**
1. 迁移可逆。
2. `upsert` + `get_by_hash` 往返一致。
3. `search_by_embedding` 能按余弦相似度返回近邻（用两条已知向量测）。
4. admin eval 不变。

**测试（前端）：** 无。

**通过标准：** 表/索引建好；数据访问层单测过；评测不回退。

### Step 2.2 三层匹配策略 CacheMatcher

**改动文件：**
- `backend/app/services/cache_matcher.py` — **新建** `QueryCacheMatcher`：三层递进（精确哈希 → 语义向量阈值 0.92 → 关键词 Jaccard 阈值 0.60）。每个候选条目过 `_is_fresh`（freshness 校验，复用文档 content hash，不新写文档服务逻辑，用现有 `document_service`）+ **`_is_level_compatible`**（请求用户安全等级 >= 缓存 `owner_security_level` 才允许命中，P4）。

**五级兼容（关键）：**
- P4：`_is_level_compatible` 保证低权限用户不会命中高权限用户的缓存答案（否则等于绕过 L5 把高等级内容泄露给低权限）。
- P1：命中后返回的 `best_answer` / `best_chunk_ids` 是当初写入时已穿透的结果，不再重新检索。

**测试（后端，新增 `backend/tests/test_cache_matcher.py`）：**
1. 精确哈希命中：同 query 二次查 → `match_type="exact_hash"`。
2. 语义命中：同义不同表述，embedding 相似度 ≥0.92 → `match_type="semantic"`。
3. 关键词命中：Jaccard ≥0.60 → `match_type="keyword_jaccard"`。
4. **等级隔离（P4）**：L1 用户查不到 `owner_security_level=L3` 的缓存条目（即使语义完全相同）→ 返回 None。
5. freshness 失效：文档 content hash 变化后 → 该条目不命中。
6. 阈值以下：相似度 0.85（在 0.80–0.92 之间）→ 不直接命中，留给 near-miss（Step 2.4）。

**测试（前端）：** 无。

**通过标准：** 三层匹配 + 等级隔离 + freshness 全部单测过。

### Step 2.3 缓存感知的 chat 链路（命中短路）

**改动文件：**
- `backend/app/api/v1/chat.py` — `_retrieve_and_generate` 入口**新增可选分支**（不改现有主流程顺序）：在 `retrieval_service.search` 之前插入"先查缓存"逻辑。命中且 `not force_refresh` → 直接用缓存的 `best_answer`/`best_chunk_ids` 构造 response（candidates 用缓存的 chunk 子集，content 仍走降级值——因缓存里存的就是降级后的），跳过 rerank+LLM。未命中 → 走原流程不变。分支用 `settings.ENABLE_QUERY_CACHE` 开关包裹，默认可关，确保不影响现有行为。

**通过标准：** 默认关闭不影响现有行为；开启后命中短路正确；等级隔离端到端生效；eval 不回退。

### Step 2.4 缓存写入策略 + near-miss + 淘汰

**五级兼容：**

**测试（后端）：**

4. freshness 失效条目被 `evict_expired` 清理。

**测试（前端）：**

2. near-miss 候选在面板里以"缓存近似"标识区分。

**通过标准：** 写入策略正确、越权不进缓存、淘汰生效、near-miss 不误命中、eval 不回退。

## 8. 风险与回退

| 风险 | 缓解 | 回退 |
|------|------|------|
| 迁移失败 | 每个迁移独立、可逆、先 downgrade 测试 | `alembic downgrade -1` |

| 流式路径不一致 | 流式不强加持久化，候选走 SSE | 非流式为主路径 |
