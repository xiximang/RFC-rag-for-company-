#### chunks — 文档片段表（核心数据）

```sql
CREATE TABLE chunks (
    id              UUID PRIMARY KEY,            -- 片段ID (chunk_id)
    doc_id          UUID REFERENCES documents(id) ON DELETE CASCADE NOT NULL, -- 所属文档
    content         TEXT NOT NULL,               -- 片段文本内容
    modality        VARCHAR(16),                 -- text/image/audio/video/table
    chunk_index     INTEGER NOT NULL,            -- 在文档中的序号
    position_info   JSONB DEFAULT '{}',          -- 位置信息（页码、段落、单元格坐标）
    vector_id       VARCHAR(255),                -- Milvus中的向量ID
    content_tsv     TSVECTOR,                    -- 全文检索向量（GIN索引）
    metadata        JSONB DEFAULT '{}',          -- 元数据（max_keyword_level/tags等）
    status          VARCHAR(16) DEFAULT 'active',-- active/inactive/deprecated
    created_at      TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_chunks_doc_id ON chunks(doc_id);
CREATE INDEX idx_chunks_content_tsv ON chunks USING GIN(content_tsv);
```

#### engineer_feedback — 工程师反馈表

```sql
CREATE TABLE engineer_feedback (
    id                      VARCHAR(36) PRIMARY KEY,
    user_id                 UUID REFERENCES users(id) NOT NULL,
    message_id              UUID REFERENCES messages(id) NOT NULL,  -- ⚠️ 当前为 NO ACTION
    query                   TEXT NOT NULL,            -- 原始查询文本
    chosen_rank             INTEGER NOT NULL,         -- 工程师选中的最佳结果排第几
    ranking                 JSONB NOT NULL,           -- 完整排序列表 [chunk_id_1, chunk_id_2, ...]
    ratings                 JSONB,                    -- 每个候选的评分 {chunk_id: 分数}
    action                  VARCHAR(32) DEFAULT 'rank',-- rank/approve/edit/force_refresh
    edited_answer           TEXT,                     -- 工程师修改后的答案
    comment                 TEXT,                     -- 备注
    reviewer_security_level VARCHAR(8),               -- 反馈者的安全等级
    created_at              TIMESTAMPTZ DEFAULT now()
);
```

| id | message_id | query | ranking | chosen_rank |
|----|-----------|-------|---------|-------------|
| fb_001 | msg_002 | "UPS5000功率" | ["chunk_001", "chunk_003", "chunk_002"] | 1 |

> ⚠️ **外键问题**：`message_id` 引用 `messages.id`，当前为 `NO ACTION`（无级联策略）。
> 删除会话 → 级联删 messages → 被 engineer_feedback 的外键阻止 → 事务崩溃。
> 反馈数据应独立于会话生命周期，建议改为 `ON DELETE SET NULL`。

## 2. 向量数据库 — Milvus（主向量存储）

### 连接信息

```
地址:  milvus-standalone:19530
集合前缀: rag_
后端切换: VECTOR_STORE_BACKEND=milvus（默认）| pgvector
```

### 集合结构

Milvus 是**列式存储的向量数据库**，每个"集合"相当于关系数据库的一张表。
每条记录是一个"实体"（entity），包含向量字段 + 标量字段。

#### Collection: `rag_text_chunks` — 文本chunk向量

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR(128) 主键 | entity ID |
| chunk_id | VARCHAR(128) | 对应 PostgreSQL chunks.id |
| doc_id | VARCHAR(128) | 所属文档ID |
| kb_id | VARCHAR(128) | 所属知识库ID |
| modality | VARCHAR(32) | 模态类型 |
| doc_acl_version | VARCHAR(128) | 文档ACL版本（权限缓存失效用） |
| max_keyword_level | INT32 | 最高敏感级别（L5过滤用） |
| tags | ARRAY\<VARCHAR(64)\> | 标签列表（L4过滤用） |
| created_by | VARCHAR(128) | 创建者 |
| status | VARCHAR(32) | active/inactive |
| **embedding** | **FLOAT_VECTOR(1024)** | **1024维稠密向量** |

索引：HNSW (M=16, efConstruction=200), COSINE 距离

#### Collection: `rag_image_frames` — 图片/视频帧向量

| 字段 | 类型 | 说明 |
|------|------|------|
| id | VARCHAR(128) 主键 | entity ID |
| chunk_id | VARCHAR(128) | 对应 chunk ID |
| doc_id | VARCHAR(128) | 所属文档ID |
| kb_id | VARCHAR(128) | 所属知识库ID |
| frame_index | INT32 | 帧序号 |
| image_url | VARCHAR(512) | 图片路径 |
| **embedding** | **FLOAT_VECTOR(512)** | **512维稠密向量** |

### 标量索引

`doc_id`, `modality`, `kb_id`, `status` 等标量字段有倒排索引。
这是"检索时前置过滤"能工作的基础——Milvus 先用这些标量索引快速过滤出有权限的向量子集，只对子集做 ANN 搜索。

### 与 PostgreSQL 的对应关系

```
PostgreSQL chunks 表（完整数据）          Milvus rag_text_chunks（向量索引）
┌────────────────────────┐              ┌────────────────────────┐
│ id (chunk_id)          │──────────────│> id / chunk_id         │
│ content（原始文本）     │              │（无原始文本，只有向量） │
│ doc_id                 │──────────────│> doc_id                │
│ modality               │──────────────│> modality              │
│ metadata->tags         │──────────────│> tags                  │
│ metadata->max_keyword  │──────────────│> max_keyword_level     │
│ content_tsv (全文索引)  │              │（无，BM25 在 PG 做）    │
│（无向量）              │              │> embedding (1024维)     │
└────────────────────────┘              └────────────────────────┘
         ↓                                       ↓
   全文检索/权限/元数据                    向量近似检索（ANN）
   用 PostgreSQL                        用 Milvus HNSW 索引
```

## 4. 缓存与消息队列

### 4.1 Redis

```
地址: redis://redis:6379/0
用途: 缓存、会话、限流计数器、分布式锁
```

#### 缓存数据类型与Key格式

| Key模式 | 类型 | TTL | 说明 |
|---------|------|-----|------|
| `user_doc_permission:{user_id}:{doc_id}` | String (ALLOW/DENY/PARTIAL) | 300s | 用户对文档的权限 |
| `user_tag_permission:{user_id}` | Hash (allowed/denied) | 300s | 用户标签权限 |
| `user_field_permission:{doc_id}:{user_id}` | String (JSON) | 600s | 字段级权限配置 |
| `user_file_types:{user_id}` | Set | 300s | 用户允许的文件类型 |
| `user_security_level:{user_id}` | String (L0-L4) | 300s | 用户安全等级 |
| `doc_acl_version:{doc_id}` | String | 86400s | 文档ACL版本号 |
| `rate_limit:{ip}` | Counter | 滑动窗口 | Kong 限流 |
| FastAPI session | — | 会话生命周期 | 用户登录状态 |

#### Redis 在系统中的角色

```
请求进入 → 查 Redis 缓存
  ├── 命中 → 直接使用，跳过 PostgreSQL 查询
  └── 未命中 → 查 PostgreSQL → 写入 Redis（设 TTL）
```

所有缓存读取都**容错降级**——Redis 不可用时返回 `None`，代码退回查 PG。

### 4.2 RabbitMQ

```
地址: amqp://rag_user:rag_password@rabbitmq:5672/
用途: Celery 异步任务的消息队列（Broker）
```

#### 队列与分发

| 队列名 | 消费者 | 任务内容 |
|--------|--------|---------|
| `ingest` | ingest-worker | 文档解析、分块、关键词标注、写库 |
| `embed` | embed-worker | 向量化 + 写入 Milvus |
| `eval` | eval-worker | 离线评测（当前未独立部署） |

#### 三类Worker分离设计

```
ingest-worker（CPU密集：解析/OCR/分块）
    队列: ingest
    资源: 1 CPU / 1.5G 内存

embed-worker（IO密集：调用 embedding API + 写 Milvus）
    队列: embed
    资源: 1 CPU / 1.5G 内存

eval-worker（算力密集：批量检索 + 生成 + 指标计算）
    队列: eval（复用了 ingest 队列）
    资源: 取决于任务量
```

> ⚠️ 当前 eval-worker 的 `task_routes` 配置中 `eval_tasks` 实际路由到了 `ingest` 队列，尚未独立。

## 数据流转全景

### 写入链路

```
用户上传文件
  → PostgreSQL: documents 表（状态 pending）
  → MinIO: 原始文件存储
  → RabbitMQ: ingest 队列
    → ingest-worker:
        → MinIO 下载 → Pipeline 解析（pdfplumber/python-docx/etc.）
        → PostgreSQL: chunks 表（含 content, content_tsv, metadata）
        → 关键词标注 → metadata.max_keyword_level / tags
    → RabbitMQ: embed 队列
      → embed-worker:
        → 调 embedding API（yunwu.ai）
        → Milvus: rag_text_chunks 集合（向量 + 标量字段）
        → PostgreSQL: documents 状态更新为 indexed
```

### 读取链路

```
用户提问 "UPS5000功率"
  → 查 Redis 缓存（三层缓存命中检查）
    → 命中 → 直接返回缓存结果
    → 未命中 → 继续
  → 查 PostgreSQL 权限表（L1/L2/L4 过滤条件）
  → 并行检索:
    ├── Milvus: ANN 搜索 + expr 权限过滤 → chunk_id 候选
    └── PostgreSQL: BM25 tsquery + WHERE 权限过滤 → chunk_id 候选
  → RRF 融合 → 加载 chunks.content → L3/L5 过滤 → Cross-Encoder Rerank
  → SecurityGateway 策略决策 → 调 LLM → 返回
  → 结果写入 Redis 缓存（供下次命中）
  → 写入 PostgreSQL: conversations/messages（对话历史）
```

## 各数据库的取舍逻辑

| 组件 | 存什么 | 为什么用它 | 不选什么 |
|------|--------|-----------|---------|
| **PostgreSQL** | 结构化业务数据、全文检索、权限、配置 | 关系模型成熟、事务ACID、JSONB灵活、pgvector降级 | — |
| **Milvus** | 向量索引（主存储） | 分布式向量检索、HNSW索引、标量+向量混合过滤 | 只用 pgvector（性能不够） |
| **MinIO** | 原始文件 | S3兼容、对象存储、与Milvus底层存储集成 | PostgreSQL 存大文件（不行） |
| **Redis** | 缓存/限流/会话 | 纯内存、微秒级访问 | RabbitMQ（不同用途） |
| **RabbitMQ** | 异步任务队列 | 可靠投递、队列隔离、Worker分离 | Redis 做队列（丢数据风险） |
